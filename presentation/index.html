02 • Business Case

Problem Statement vs. Solution

Bridging the gap between manual event operations and automated enterprise customer experience.

✕
Traditional Challenges
  • Ticket Overselling & Race Conditions: Concurrent users checking out simultaneously exhaust venue capacity, causing embarrassing booking conflicts.
  • Disjointed Budget Approval: High-value corporate events require manual email chains for manager approvals before publication.
  • Clunky Registration UX: Standard CRM forms look like internal databases rather than modern, consumer-ready ticketing apps.
  • Manual Follow-ups & Reminders: Staff forget to issue reminder emails 24 hours prior or dispatch post-event feedback surveys.
✓
Salesforce CRM Solution
  • Atomic Database Locking: Apex SELECT ... FOR UPDATE locks ticket quotas at the row level, mathematically eliminating oversell risks.
  • Automated Approval Matrix: Low-budget events auto-approve instantly; budgets exceeding threshold trigger Salesforce Approval Processes.
  • Consumer-Grade LWC Portal: Real-time category filtering, responsive card decks, guest ticket quantity selection, and simulated UPI/QR payment.
  • Hands-Free Automated Lifecycle: Scheduled Flows automatically batch 24-hour reminders and post-event survey invitations without human effort.

Core Custom Objects & Cardinality
Parent Object Relationship Child Object Purpose
Event__c 1 : Many (Lookup) Ticket_Type__c Multiple pricing tiers (VIP, General)
Event__c Many : 1 (Lookup) Venue__c Physical location & capacity limits
Event__c 1 : Many (Lookup) Registration__c Attendee booking attempts (Pending/Confirmed)
Registration__c 1 : 1 (Lookup) Ticket__c Issued admission pass with unique barcode ID
Registration__c 1 : 1 (Lookup) Payment__c Transactional payment confirmation record
Registration__c 1 : 1 (Lookup) Feedback__c Post-event survey rating & attendee review
Design Rationale: Master-Detail vs. Lookup
  • Why Lookup for Ticket_Type__c: Enables independent archiving, security permissions, and prevents accidental deletion cascades of active tickets.
  • Inventory Roll-Up Design: Because Registration__c $\rightarrow$ Ticket_Type__c is a Lookup, Booked_Seats__c is managed atomically in the Apex trigger rather than standard declarative rollups.
  • Deduplicated Attendee Master: Attendee__c records are unified by email address. One attendee can register for dozens of events without duplicating their core profile.

08 • Senior Engineering

Transaction Safety & Concurrency Locking

How we solved the classic last-seat race condition problem natively on the Salesforce platform.

The Concurrency Flaw with Flows & VRs

Validation Rules and Flows evaluate data against the start-of-transaction snapshot. If User A and User B both submit for the last seat at 12:00:00.000:

  • Both transactions read Available_Seats__c = 1.
  • Both transactions evaluate the quota check as Valid.
  • Both insert registrations $\rightarrow$ Venue is oversold by 1 seat!
Our Apex Row-Level Locking Architecture
// RegistrationTriggerHandler.cls Map<Id, Ticket_Type__c> locked = new Map<Id, Ticket_Type__c>([ SELECT Id, Quota__c, Booked_Seats__c, Status__c FROM Ticket_Type__c WHERE Id IN :ticketTypeIds FOR UPDATE // <-- ATOMIC ROW LOCK ]);

FOR UPDATE forces the database to block Thread B until Thread A commits. Thread A claims the seat; Thread B wakes up, detects Available = 0, and receives a clean "Sold Out" exception!

09 • Lifecycle Automation

Post-Booking & Bulkified Scheduled Flows

Decoupled execution engine guaranteeing ticket delivery and governor-limit-safe background batches.

Record-Triggered Flow (Post-Registration)
  • Fires After Save when status changes to Confirmed.
  • Step 1: Creates Ticket__c record with status Active.
  • Step 2: Logs completed audit Task on the Event record.
  • Step 3: Dispatches Ticket Confirmation Email containing Ticket ID.
  • Fault Handling: Includes <faultConnector> setting Confirmation_Status__c = 'Failed' if delivery fails.
Bulkified Scheduled Background Flows
  • Zero SOQL in Loop: Initial query filters Feedback_Submitted__c = false directly upfront, eliminating in-loop database calls.
  • Batch Email Delivery: In-memory string collection accumulates all recipient addresses and fires one single email invocation outside the loop.
  • Governor Limit Proof: Consumes 1 of 10 email calls, completely impervious to the 10-email-per-transaction limit!
10 • Platform Governance

Security Model, OWD & Persona Matrix

Role-based access control safeguarding financial data and enforcing organizational boundaries.

Organization-Wide Defaults (OWD)
Object OWD Setting Visibility Strategy
Event__c Public Read Only Visible to all for browsing; editable only by Organizer/Manager
Registration__c Private Users see only their own registrations (or assigned team)
Payment__c Private Strictly restricted to Event Managers and Finance auditors
Venue__c Public Read Only Shared reference catalog across all organizers
User Persona Matrix
  • Event Organizer: Can propose events, set quotas, and view registrations for their own events. Cannot approve their own high-budget proposals.
  • Event Manager: Has elevated managerial permissions. Reviews and approves proposed budgets, manages venue contracts, and reviews financial payments.
  • Attendee (Public Portal): Can search published events, register, submit payments, view tickets, and submit feedback. Zero access to backend CRM configs.
